## 1. The Integration Problem

The Digital Twin (B3 in the organisational model) requires a running Cosolvent instance populated with:
- **Knowledge Slot content (B1)** — reference documents, curated domain knowledge
- **Synthetic participants (B2)** — realistic user profiles generated by ClientSynth

For the synthetic profiles to be useful, they must:
1. **Conform to the vertical's `marketplace.yaml` profile schemas** — same field names, same types, same allowed values
2. **Pass Cosolvent's validation** — the dynamic Pydantic model built by `schema_engine.py`
3. **Be indexable by the vector pipeline** — `indexer.py` builds embeddings from searchable fields
4. **Produce meaningful matches in discovery** — the gallery, search, and RAG system should work as if real users filled out the profiles
5. **Cover all participant types** — the correct distribution of supply, demand, and facilitator roles
6. **Never be confused with real users** — per GEMINI.md, synthetic profiles are for test/demo environments only

Currently, **zero integration exists**. ClientSynth and Cosolvent have no shared code, no shared file format, no API contract, and no awareness of each other's data models.

## 2. How Cosolvent Stores and Uses Profiles

### Storage: Document-Store Pattern

Cosolvent uses a **document-store pattern on PostgreSQL**. All collections (users, profiles, drafts, applications, etc.) share the same table structure:

```
┌──────────────────────────────────────────┐
│  profiles (DOCUMENT_COLLECTIONS table)    │
├────────┬─────────────────────────────────┤
│ id     │ UUID (PK)                        │
│ data   │ JSONB — the entire profile doc   │
│ created_at │ TIMESTAMPTZ                  │
│ updated_at │ TIMESTAMPTZ                  │
└────────┴─────────────────────────────────┘
```

Everything about a profile lives inside the `data` JSONB column:

```json
{
  "user_id": "uuid-of-the-user",
  "participant_type": "producer",
  "status": "active",
  "fields": {
    "farm_name": "Prairie Gold Farms",
    "country": "Canada",
    "region": "Saskatchewan",
    "primary_crops": ["Wheat", "Barley"],
    "description": "Third-generation grain farm...",
    "annual_production": 5000,
    "certifications": ["Organic", "Non-GMO"],
    "protein_content": "12-14%",
    "storage_capacity": 8000
  },
  "ai_profile": "Prairie Gold Farms is a ...",
  "ai_profile_draft": null,
  "ai_profile_status": "approved",
  "ai_profile_updated_at": "2026-01-15T...",
  "completeness": 100,
  "created_at": "2026-01-10T...",
  "updated_at": "2026-01-15T..."
}
```

### Profile Lifecycle

```
Registration → Draft → Submit → [Application → Approval] → Profile → Index
                                        ↑                       │
                                  (if requires_approval)        │
                                                                ▼
                                                        profile_vectors
                                                        (embedding + metadata)
```

1. **Registration** (`register()` in `service.py`): Creates an empty draft with `participant_type` from the user record
2. **Draft editing** (`update_draft()`): User fills in field values; validated against `marketplace.yaml` schema via `validate_profile_fields()`
3. **Submission** (`submit_draft()`): Checks completeness threshold; if `requires_approval: true`, creates an application for admin review; otherwise auto-creates the profile
4. **Indexing** (`_queue_profile_index()` → `index_profile()`): Builds a text representation from all `searchable: true` fields + the `ai_profile` narrative, generates an embedding via `text-embedding-3-small`, upserts to `profile_vectors` table

### Validation Pipeline

```python
# schema_engine.py
_TYPE_MAP = {
    "text": str, "rich_text": str, "number": float,
    "select": str, "multi_select": list[str],
    "date": str, "file": str, "location": dict
}

# Dynamically builds a Pydantic model from marketplace.yaml field definitions
# Required fields must be present; optional fields default to None
# Type coercion: "number" fields must be float-compatible, etc.
```

**Key constraint:** The validation only checks types and required-ness. It does **not** validate `select` options against the allowed values list, or `multi_select` values against their options. This means ClientSynth could technically insert invalid option values and pass validation — but they'd produce garbage in search filters and gallery display.

### Vector Indexing

```python
# indexer.py — builds embedding text like:
# "Farm Name: Prairie Gold Farms\nCountry: Canada\nPrimary Crops: Wheat, Barley\n..."
# Only fields with searchable: true are included
# The ai_profile narrative is appended if present

# vector_metadata stored alongside embedding:
# {"participant_type": "producer", "country": "Canada", "primary_crops": ["Wheat", "Barley"], ...}
```

**Key constraint:** Vector metadata uses the **raw field values** from the profile. The discovery system's `_apply_profile_field_filters()` queries against the canonical `profiles.data["fields"]` JSONB, using `contains` semantics that support both scalar and array matching. If ClientSynth uses "Wheat" but the filter expects "wheat", matching breaks.

### Discovery and Search

The gallery and RAG search use `search_profile_vectors_strict()`:
1. Filter by `participant_type` (must be in `searchable_types` from config)
2. Filter by profile field filters (`country`, `primary_crops`, `certifications` per `filter_fields` in config)
3. Rank by cosine similarity to query embedding
4. Join back to canonical profile data for display

## 3. How ClientSynth Generates Data

### Current Architecture

ClientSynth is a **general-purpose synthetic data generator**. It has no concept of "marketplace participants." Its data model is:

```
Schema → Job → Generated Records (→ Export)
```

| Concept              | What It Is                                                              | Cosolvent Equivalent                               |
| -------------------- | ----------------------------------------------------------------------- | -------------------------------------------------- |
| **Schema**           | A user-defined list of fields with types, descriptions, and constraints | `profile_schemas` section of `marketplace.yaml`    |
| **Field**            | A named data element (name, type, description, example values)          | A `FieldDefinition` in `ProfileSchema`             |
| **Job**              | A request to generate N records from a schema                           | No equivalent (profiles are created one-at-a-time) |
| **Generated Record** | A JSON object with values for each field                                | A profile's `fields` dict                          |
| **Export**           | CSV/JSON/XLSX/SQL output of generated records                           | No equivalent (profiles are stored in DB)          |

### Generation Pipeline

```
For each record in the job:
  For each field in the schema:
    1. Build context (field type, description, existing data, examples)
    2. Build system prompt (type-specific instructions)
    3. Build user prompt (field context + previously generated values + examples)
    4. Call OpenRouter API (Gemini 2.5 Flash)
    5. Parse and clean the response
    6. Store in generated_data table
```

### What ClientSynth Does Well

- **Field-type-aware generation** — different system prompts for name, email, phone, company, text, number, etc.
- **Example data incorporation** — uploaded example values guide generation style
- **Data quality controls** — distribution manager, pattern detector, similarity scorer, cooldown tracker prevent repetitive outputs
- **Multi-format export** — CSV, JSON, XLSX, SQL, XML, Parquet
- **Image and PDF generation** — can generate profile photos and supporting documents

### What ClientSynth Lacks for Cosolvent Integration

| Capability                                     | Status | Why It Matters                                                                 |
| ---------------------------------------------- | ------ | ------------------------------------------------------------------------------ |
| **`marketplace.yaml` awareness**               | ❌ None | Cannot auto-generate schemas conforming to Cosolvent's profile definitions     |
| **Participant type concept**                   | ❌ None | All records are flat; no notion of supply/demand/facilitator roles             |
| **`select`/`multi_select` option constraints** | ❌ None | ClientSynth fields have no allowed-values lists from config                    |
| **Inter-record relationships**                 | ❌ None | Generated records are independent; no buyer/seller market coherence            |
| **Population-level quality**                   | ❌ None | Quality scoring is per-record, not per-population                              |
| **`ai_profile` narrative generation**          | ❌ None | Cosolvent profiles use AI-generated narrative text for vector indexing         |
| **Cosolvent-format export**                    | ❌ None | No export mode that produces Cosolvent's `profiles` JSONB format               |
| **Embedding generation**                       | ❌ None | Cannot produce `profile_vectors` rows; Cosolvent must re-index after import    |
| **User account creation**                      | ❌ None | Cosolvent profiles require a corresponding `users` row with `participant_type` |
| **Visibility tier awareness**                  | ❌ None | ClientSynth doesn't know which fields are public/protected/private             |
| **Onboarding bypass**                          | ❌ None | No path to skip the draft → submit → approve lifecycle for bulk import         |

## 5. Schema Conformance: The Central Challenge

The hardest integration problem is ensuring that generated profiles **conform to the vertical's `marketplace.yaml`**. This is structurally identical to the Knowledge Slot's shared vocabulary problem (Gotcha 6 in the Knowledge Slot integration notes).

### What "Conformance" Means

For a grain trading producer profile to work in Cosolvent, the generated data must satisfy:

```yaml
# From marketplace.example.yaml — producer profile schema
fields:
  - name: farm_name        # type: text, required: true
  - name: country          # type: select, options: [Canada, USA, Brazil, Australia, Argentina]
  - name: region           # type: text
  - name: primary_crops    # type: multi_select, options: [Wheat, Barley, Canola, Oats, Lentils, Peas, Flax]
  - name: description      # type: rich_text
  - name: annual_production # type: number
  - name: certifications   # type: multi_select, options: [Organic, Non-GMO, Fair Trade, ISO 22000]
  - name: protein_content  # type: text
  - name: storage_capacity # type: number
  - name: financial_notes  # type: text, visibility: private
```

ClientSynth must:
1. Use **exactly these field names** (`farm_name`, not `farmName` or `Farm Name`)
2. Use **exactly these option values** (`"Canada"`, not `"CA"` or `"canada"`)
3. Respect **field types** (number fields get numbers, not strings)
4. Respect **required/optional** (all required fields must be filled for completeness ≥ threshold)
5. Produce **realistic combinations** (a Canadian farm shouldn't list Brazilian certifications)

### Three Approaches to Schema Conformance

| Approach                                          | How It Works                                                                                       | Effort | Fidelity                                                      |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------- | ------ | ------------------------------------------------------------- |
| **Manual schema mirroring**                       | Developer manually creates a ClientSynth schema that mimics the `marketplace.yaml` fields          | Low    | Low — drift risk, no auto-validation                          |
| **Config import (C1.1 from ClientSynth roadmap)** | ClientSynth imports `marketplace.yaml` and auto-generates a conforming schema per participant type | Medium | High — field names, types, and options are guaranteed correct |
| **API-driven generation**                         | Cosolvent exposes a "generate synthetic profile" endpoint that calls ClientSynth as a service      | High   | Highest — generation + validation + indexing in one step      |

**Recommended phase-in:**
1. **Now:** Manual schema mirroring for C0 (file-based integration)
2. **C1.1:** Config import — ClientSynth reads `marketplace.yaml` programmatically
3. **C2:** API-driven — full bidirectional integration

### The `select` / `multi_select` Problem

ClientSynth's schema builder supports field types like `text`, `email`, `number`, etc. — but its `enum` type is the closest analog to Cosolvent's `select`/`multi_select`. The critical difference:

| Cosolvent                                                      | ClientSynth                                                            |
| -------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `type: select, options: [A, B, C]` — exactly one of A, B, or C | `type: enum` with example values — AI generates similar-looking values |
| `type: multi_select, options: [A, B, C]` — subset of A, B, C   | No equivalent — no multi-value field type                              |

**The risk:** If ClientSynth treats `select` as a freeform text field guided by examples, it might generate `"Saskatchewan Wheat"` instead of `"Wheat"` for `primary_crops`. This passes ClientSynth's internal validation but breaks Cosolvent's filter system.

**Mitigation for C0:** Hard-code the allowed values into the ClientSynth schema as strict enums. For C1.1, import them programmatically from `marketplace.yaml`.

### The Import Script: What It Must Do

The `load-synthetic-participants.py` script (living in the vertical project's B2 directory) must perform these operations against Cosolvent's database:

```python
# Pseudocode for the import script

for record in clientsynth_export:
    # 1. Create synthetic user
    user_id = insert_into("users", {
        "email": f"synthetic-{uuid4()}@digital-twin.test",
        "password_hash": bcrypt("synthetic-placeholder"),
        "participant_type": record["_participant_type"],
        "role": "user",
        "is_synthetic": True,  # ← marker field
        "display_name": record["fields"]["farm_name"],  # or org_name
    })

    # 2. Build profile fields (only Cosolvent-known fields)
    fields = {k: v for k, v in record["fields"].items()
              if k in marketplace_config.profile_fields_for(record["_participant_type"])}

    # 3. Generate ai_profile narrative
    ai_profile = generate_narrative(fields, record["_participant_type"])

    # 4. Compute completeness
    completeness = compute_completeness(marketplace_config, record["_participant_type"], fields)

    # 5. Insert profile
    profile_id = insert_into("profiles", {
        "user_id": str(user_id),
        "participant_type": record["_participant_type"],
        "status": "active",
        "fields": fields,
        "ai_profile": ai_profile,
        "ai_profile_status": "approved",
        "completeness": completeness,
    })

    # 6. Generate and insert embedding
    embedding = get_embedding(build_searchable_text(fields, ai_profile, marketplace_config))
    insert_into("profile_vectors", {
        "profile_id": profile_id,
        "embedding": embedding,
        "vector_metadata": build_vector_metadata(fields, record["_participant_type"]),
    })
```

### The `is_synthetic` Marker

Cosolvent currently has no concept of synthetic vs. real users. The import script must add a marker so that:
1. **Cleanup is possible** — `DELETE FROM profiles WHERE data->>'is_synthetic' = 'true'`
2. **The GEMINI.md restriction is enforceable** — a production deployment can verify it has zero synthetic users
3. **Admin UI can distinguish** — optional visual indicator for test/demo environments

**This requires a small addition to Cosolvent** — not a schema change (JSONB is flexible), but a convention that the `data` column can contain `is_synthetic: true` on both users and profiles.

The import script should be **generic**, parametrised by:
1. The `marketplace.yaml` path (knows field names, types, allowed values, participant types)
2. The ClientSynth export file path
3. A mapping file that tells the script which exported fields map to which Cosolvent profile fields (or defaults to same-name mapping)

```
load-synthetic-participants.py \
  --config marketplace.yaml \
  --export clientsynth-output.json \
  --mapping field-mapping.yaml \      # optional, for field name translation
  --participant-type producer \
  --count 50
```

## 8. Overlaps with Knowledge Slot Integration

The ClientSynth integration shares several concerns with the Knowledge Slot integration. These should be solved once, not twice:

### Overlap 1: Shared Vocabulary

**Knowledge Slot problem:** Reference documents tagged with `origin_country: "United States of America"` won't match profiles with `country: "USA"`.

**ClientSynth problem:** Generated profile fields must use the exact option values from `marketplace.yaml`. If ClientSynth generates `"Saskatchewan Wheat"` instead of `"Wheat"`, search filters break.

**Shared solution:** Both integrations need a **controlled taxonomy** that normalises vocabulary across `marketplace.yaml`, Knowledge Slot metadata, and ClientSynth generation. This should be a shared YAML file in the vertical project:

```yaml
# shared_taxonomies.yaml
countries:
  - { value: "Canada", aliases: ["CA", "CAN"] }
  - { value: "USA", aliases: ["US", "United States", "United States of America"] }
crops:
  - { value: "Wheat", aliases: ["wheat", "HRS Wheat", "Hard Red Spring"] }
```

### Overlap 2: `marketplace.yaml` as Source of Truth

Both integrations consume `marketplace.yaml`:
- **Knowledge Slot:** Uses profile field definitions to build `reference_metadata_schema` and `user_context_mapping`
- **ClientSynth:** Uses profile field definitions to constrain generated values

Both need a **programmatic reader** for `marketplace.yaml` that extracts:
- Field names, types, required/optional status
- Allowed values for select/multi_select fields
- Participant types and their roles
- Searchable/visibility attributes

ClientSynth is TypeScript; Cosolvent is Python. The YAML file is the interface — both must parse it correctly. This is already true (YAML is a standard format), but it means the `marketplace.yaml` spec is a **shared contract** that must be documented and versioned.

### Overlap 3: Embedding Model Lock-In (Conflict C4)

Both Knowledge Slot chunks and profile vectors use `text-embedding-3-small` (1536 dimensions). The import script for synthetic profiles must use the **same model and dimension** as the indexer.

If the embedding model changes in a future Cosolvent version, both the Knowledge Slot ingestion pipeline and the ClientSynth import script break simultaneously.

**Shared mitigation:** The embedding model should be a configuration value (in `marketplace.yaml` or environment), not hardcoded in `indexer.py`. Both integrations should read from the same config.

### Overlap 4: Vertical Isolation

Both integrations must ensure that a grain trading vertical's synthetic users and reference documents never contaminate a mental health vertical. The organisational model (A/B/B1/B2/B3) handles this naturally — separate Cosolvent instances per vertical. But if Option C (shared infrastructure, isolated data) is ever pursued, both need `vertical_id` scoping.

### Overlap 5: Seed Data Loading

The Knowledge Slot needs a mechanism to load reference documents into a Cosolvent instance. ClientSynth needs a mechanism to load synthetic profiles. Both are "seed data" operations for the Digital Twin.

**Shared solution:** A single **Digital Twin bootstrapping CLI** that:
1. Loads `marketplace.yaml` configuration
2. Loads Knowledge Slot content (B1) into `reference_documents` / `reference_chunks`
3. Loads synthetic profiles (B2) into `users` / `profiles` / `profile_vectors`
4. Validates the population (completeness, vector coverage, filter test)

```bash
cosolvent bootstrap-twin \
  --config marketplace.yaml \
  --knowledge-slot ./knowledge-slot/seed-data/ \
  --synthetic-profiles ./clientsynth/output/
```

## 9. Architectural Gotchas

### Gotcha 1: ClientSynth Generates Records, Not Users

Cosolvent's profile system is built around a user lifecycle: registration → draft → submit → approve → profile. Synthetic profiles need to **bypass this entire lifecycle** and go straight to `status: "active"` profiles with corresponding user accounts.

**This is a deliberate shortcut.** It's safe because synthetic environments are isolated (GEMINI.md restriction). But it means the import script must:
- Create user records directly (bypassing registration)
- Create profile records directly (bypassing onboarding)
- Skip the application/approval step
- Manually trigger vector indexing

**Risk:** If Cosolvent later adds lifecycle hooks (e.g., "send welcome email on profile creation"), the import script will trigger them unless it explicitly bypasses them.

**Mitigation:** The import script should use a `SYNTHETIC_IMPORT=true` environment flag. Cosolvent services should check this flag before firing side effects.

### Gotcha 2: The `ai_profile` Narrative Gap

Cosolvent's vector indexing depends heavily on the `ai_profile` field — a rich text narrative generated by Cosolvent's AI profile generation feature (`ai_generate_profile()` in service.py). This narrative is what makes vector search semantic rather than keyword-based.

ClientSynth generates structured field values but has **no concept of profile narratives**. Options:

| Option                                             | How                                                                     | Pros                                  | Cons                                                            |
| -------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------- | --------------------------------------------------------------- |
| **A — Import script generates narratives**         | Script calls OpenAI with a prompt template and the generated fields     | Simple, one-time cost                 | Adds AI cost to import; narrative quality depends on prompt     |
| **B — ClientSynth generates narratives**           | Add a "profile_narrative" field type that synthesises from other fields | Reusable, part of generation pipeline | Requires ClientSynth feature development (S1.3 computed fields) |
| **C — Cosolvent generates narratives post-import** | After import, call `ai_generate_profile()` for each synthetic profile   | Uses existing Cosolvent logic         | Requires running Cosolvent to be up; N×API calls                |

**Recommended:** Option A for C0 (simplest), migrate to Option B when ClientSynth supports computed/derived fields (S1.3).

### Gotcha 3: No Batch Import API

Cosolvent has no admin API for bulk profile import. Profiles are created one-at-a-time through the onboarding flow. The import script must write directly to the database.

**This is acceptable for C0** (test/demo only). For C2 (API-driven integration), Cosolvent needs a `POST /api/admin/profiles/import` endpoint that:
- Accepts an array of profile objects
- Validates each against the config schema
- Creates user + profile + vector records
- Returns a summary (created, skipped, errors)

### Gotcha 4: Embedding Cost for Large Populations

Generating embeddings for synthetic profiles requires one OpenAI API call per profile. For 50 profiles, this is negligible (~$0.01). For population-scale testing with 1000+ profiles, costs add up and rate limits may apply.

**Mitigation:** The import script should generate embeddings in batches (OpenAI supports batch embedding) and cache them alongside the export so re-imports don't re-generate embeddings.

### Gotcha 5: Photo and Document Generation

ClientSynth can generate AI profile photos and PDF documents. Cosolvent stores these as:
- Profile photo: URL in the `fields` dict (if a `file` type field exists)
- Supporting documents: `files` collection with S3 URLs

For the Digital Twin, synthetic participants should have realistic photos and documents. But:
- ClientSynth stores generated images in its own S3 bucket
- Cosolvent expects images in its own S3 bucket (or a public URL)

**Mitigation for C0:** Use public URLs from ClientSynth's S3 bucket. For production-grade Twins, copy assets to Cosolvent's S3 bucket during import.

### Gotcha 6: Population Coherence

The Digital Twin's value depends on the synthetic population being **market-realistic**:
- Buyers' `crops_of_interest` should overlap with producers' `primary_crops`
- Geographic distribution should create viable trading corridors
- Facilitator coverage should match the trade flows
- Total supply capacity should roughly match demand

ClientSynth currently generates records **independently** — each record is statistically independent of every other. This produces populations where:
- All producers might grow wheat (no diversity)
- No buyer wants what any producer grows (no matchability)
- All facilitators are in the same city (no coverage)

**This is the single most important feature gap for Digital Twin quality.** It maps to ClientSynth roadmap items C2.1 (scenario definitions) and C2.3 (inter-participant consistency).

**Mitigation for C0:** Use distribution controls in ClientSynth (the `distribution-manager.ts` already exists) to set target distributions for key fields. For example, set `primary_crops` to 40% Wheat, 25% Barley, 20% Canola, 15% Other. This doesn't guarantee coherence but improves diversity.

## 10. Questions for Review

### Schema & Data Model

1. **`is_synthetic` marker** — Should Cosolvent's data model formally support an `is_synthetic` flag on users and profiles? Or is this purely an import-script convention stored in the JSONB?

2. **Bypass onboarding** — Should Cosolvent support a `SYNTHETIC_IMPORT` mode that skips lifecycle hooks (welcome emails, approval workflows)? Or should the import script simply not trigger those code paths?

3. **`ai_profile` generation** — Where should the narrative be generated? Import script, ClientSynth, or Cosolvent post-import? (Affects cost and architecture)

### Integration Approach

4. **C0 timeline** — The ClientSynth roadmap estimates C0 (file-based integration) at 5–9 days, involving documenting the participant schema (C0.1), adding a Cosolvent export format (C0.2), creating a schema template (C0.3), writing the import script (C0.4), and end-to-end validation (C0.5). Is this the right priority given current roadmap state?

5. **Where does the import script live?** — Options: (a) in the vertical project's B2 directory, (b) in the Cosolvent repo as a utility, (c) in the ClientSynth repo as an export plugin. Recommendation: (a) for vertical-specific scripts, with a generic template in (b).

6. **Batch import API** — Should Cosolvent expose a `POST /api/admin/profiles/import` endpoint for bulk profile creation? This would benefit both synthetic imports and future real user migration.

### Population Quality

7. **Population coherence** — How important is inter-record consistency for the initial Digital Twin demo? Options: (a) use distribution controls for now, (b) implement scenario definitions (C2.1) before first demo.

8. **Target population size** — What's the initial target? 50 profiles (demo-scale), 200 profiles (functional test), 1000+ profiles (stress test)? This affects embedding costs and generation time.

### Shared Infrastructure

9. **Shared taxonomy file** — Should the vertical project maintain a `shared_taxonomies.yaml` used by both Knowledge Slot metadata tagging and ClientSynth generation? Or is the `marketplace.yaml` sufficient as the single source of truth?

10. **Bootstrap CLI** — Should there be a single `cosolvent bootstrap-twin` command that loads both Knowledge Slot content and synthetic profiles? Or separate scripts for each?
